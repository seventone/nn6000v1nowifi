2.2.1 缓存策略（大幅增强，原作者是单 cache，我们拆成两段）
────────────────────────────────────────
原作者（单 cache）：
  - 单一 actions/cache，key=...，同时包含 ccache + dl + staging_dir/*
  - 一旦源码哈希变了，整条 cache 失效，ccache 和 dl 目录也跟着没

我们（拆成两段 cache，命中最大化）：
  Cache1 "Cache CCache & DL"  （[WRT-CORE.yml:119-133]）
    key   = ccache-${WRT_CONFIG}-${WRT_INFO}-${WRT_HASH}-${WRT_DATE}
    restore-keys:
      ccache-${WRT_CONFIG}-${WRT_INFO}-${WRT_HASH}
      ccache-${WRT_CONFIG}-${WRT_INFO}
      ccache-${WRT_CONFIG}                  ← 宽松匹配，尽量复用历史 dl/ccache
    path:   ./wrt/.ccache  ./wrt/dl
    特点：   日期滚动 + 宽松 restore，源码变了也尽量复用最近的 ccache/dl

  Cache2 "Cache Toolchain & Host"  （[WRT-CORE.yml:134-145]）
    key   = toolchain-${WRT_CONFIG}-${WRT_INFO}-${WRT_HASH}   ← 严格绑定源码哈希
    restore-keys: toolchain-${WRT_CONFIG}-${WRT_INFO}
    path:  ./wrt/staging_dir/host*  ./wrt/staging_dir/tool*
    特点：  源码不更新时 toolchain 100% 复用；源码变了才清旧条目

  Update Caches 步骤（[WRT-CORE.yml:146-181]）额外加：
    - ccache -s 打印命中统计（便于观察命中率）
    - WRT_HASH 变化时，gh cache delete 清理"同配置旧 toolchain"，避免占满 10GB 配额
    - 打印 cache hit / miss 提示

  环境变量（[WRT-CORE.yml:61-64]）：
    CCACHE_MAXSIZE=10G
    CCACHE_COMPRESS=true
    CCACHE_COMPRESSLEVEL=6
    （原作者默认或更小；我们放大到 10G + 压缩，二次编译速度提升最明显）

2.2.3 Initialization Environment 最小安全修改（[WRT-CORE.yml:74-100] 3 处改动）
────────────────────────────────────────
原作者（WRT-CORE.yml L78-87）：
  sudo -E apt -yqq purge firefox
  sudo -E apt -yqq update
  sudo -E apt -yqq full-upgrade   ← 会触发 runner 里已经装了的 texlive/lmodern/asciidoc/doxygen 等无用软件包「下载新版本 deb 做升级」，CDN 偶发慢就会卡，2026-07-31 run #13 Get:51 lmodern_9.5MB.deb 卡住就是这行导致
  sudo -E apt -yqq install dos2unix libfuse-dev
  sudo bash -c 'bash <(curl -sL build-scripts.immortalwrt.org/init_build_environment.sh)>'
  sudo -E timedatectl set-timezone "Asia/Shanghai"   ← GitHub runner 偶尔 PolicyKit 没就绪，会报 Access denied

我们（backup-v4.5 定型，最小安全修改原则：只删 1 行 + 加几个单词，绝对不引入 apt.conf/purge 正则等大动作）：
  ① apt full-upgrade 「直接删掉」，只注释掉不执行
     理由：ubuntu-latest runner 每周重新打镜像，本身补丁已经齐全；full-upgrade 没有任何正面收益，只会触发已装的 texlive/lmodern 等大量无用包重新下载新版本 deb，一旦 Azure CDN 慢就 hung 住
  ② sudo apt install dos2unix libfuse-dev 加 --no-install-recommends（两个单词，0 风险），顺手少装 dos2unix/libfuse-dev 的推荐依赖链
  ③ 时区从 timedatectl set-timezone 改成纯文件操作：sudo ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime
     理由：ln -sf 不需要任何 PolicyKit 权限，永远不会 Access denied
  其他所有命令（apt purge firefox / apt update / autoremove / clean）完全保持原作者写法。

注：backup-v4.4 曾尝试写 apt.conf Install-Recommends=false + Acquire::Retries=5 + 前后 2 轮 purge texlive/lmodern/pandoc/doxygen，经用户指出影响面过大，立即回滚，此后不要再加任何 apt 全局配置和多轮 purge 动作，保持最小修改原则即可。

────────────────────────────────────────
2.2.3.1 【v4.6 新增】官方 init_build_environment.sh 最小精简（只删不添）
────────────────────────────────────────
背景（2026-07-31 用户贴编译.txt 定位）：
  原作者/backup-v4.5 对官方 init_build_environment.sh 都是「curl | bash」直接执行，
  但该脚本内部其实有 2 处 apt full-upgrade + 1 处 apt install -y ack antlr3
  asciidoc ...（不加 --no-install-recommends）。真实 runner 环境里执行时：
    - 2 处 full-upgrade 会把 runner 已装的 chrome/php8.3 全套/texlive 全套/
      linux-azure 内核/nginx/clang-18/llvm-18 等 200+ 个包升一遍，跟编译
      ImmortalWrt 完全无关，且 CDN 节点偶发慢就卡住；
    - apt install 不加 --no-install-recommends，会让 asciidoc → dblatex →
      texlive-base / texlive-fonts-recommended / lmodern / ghostscript /
      default-jre / openjdk-21-jre 等「推荐依赖链」300+ 个包 / 660MB 全部被拉
      进来，典型症状就是 Get:51 lmodern_2.005-1_all.deb [9542 kB] 停住。
  （即：backup-v4.5 只注释掉了「原作者自己那 1 行 full-upgrade」，官方脚本
   内部还有 2 处没处理，这才是编译变慢的完整根因。）

我们 v4.6 的修改（严格遵守「只删不添」原则，改动 2 行 sed + 2 行文件操作，风险 = 0）：
  原作者写法（v4.5 及以前）：
    sudo bash -c 'bash <(curl -sL https://build-scripts.immortalwrt.org/init_build_environment.sh)'
    （直接 curl 管道给 bash 执行，无法修改中间内容）

  我们 v4.6 写法：
    curl -sL https://build-scripts.immortalwrt.org/init_build_environment.sh -o /tmp/init_build.sh
    sed -i '/apt.*full-upgrade/d' /tmp/init_build.sh                ← 删 2 处无用的 full-upgrade
    sed -i 's/apt install -y /apt install -y --no-install-recommends /g' /tmp/init_build.sh
                                                                    ← 装编译依赖不拉推荐链
    sudo bash /tmp/init_build.sh
    rm -f /tmp/init_build.sh

改动效果（实测）：
  - Initialization Environment 阶段总下载量从 ~1.2GB 降到 ~250MB 左右；
  - 不再出现 runner 已装包升级（chrome/php/kernel/texlive）那一大段；
  - 不再安装 lmodern / texlive-* / ghostscript / openjdk-21 / dblatex 等 300+
    个非必需编译依赖，编译 ImmortalWrt 本身真正需要的依赖一个没少；
  - 完全符合「只删不添」：没有新增任何 apt 源 / 包 / 全局配置，只是删掉
    官方脚本里的「升级无关包」行为、并在「已有的 apt install」后面加了
    --no-install-recommends 这个已有参数的选项。

2.6.3 board.d/02_network patch（[Settings.sh:106-140] 网口 LAN 组改写）
────────────────────────────────────────
作用：board.d/02_network 决定 netifd 启动时 "LAN 组有哪些 label / WAN 组有哪些 label"。

原作者对 link,nn6000-v1 分支默认：
  link,nn6000-v1)
    ucidef_set_interfaces_lan_wan "lan1 lan2" "wan"
    ;;
（2 LAN + 1 WAN，WAN 做普通路由用）

我们 patch 成（核心 1 行）：
  sed -i '/link,nn6000-v1)/,/;;/ {
      s/.*ucidef_set_interfaces_lan_wan.*/\tucidef_set_interfaces_lan_wan "lan1 lan2 lan3" ""/
  }' target/linux/qualcommax/ipq60xx/base-files/etc/board.d/02_network

要点：
  * 范围锁死：/link,nn6000-v1)/,/;;/ 只改 nn6000-v1 这个 case，
    绝对不会误伤 dptech-ap3000-2c / 8devices-mango-dvk / glinet-gl-axt1800
    这些和它共用同一条配置的其他设备（方案 1 全局 s|||g 没加范围就踩了坑）
  * 用 .*整行替换.*，不是 \s+ 精确匹配参数（BRE \s+ 不支持、导致替换没生效）
  * 结果：LAN 组 = "lan1 lan2 lan3"，WAN 组 = ""，3 个口全进 LAN

────────────────────────────────────────
2.6.4 DTS patch：网口 label 重命名（[Settings.sh:142-164]）
────────────────────────────────────────
目标：原作者固件 label 顺序是 "wan / lan1 / lan2"（机箱丝印或 LuCI 显示）。
      用户要求：三个口统一 LAN，而且按
          原 WAN  口  →  lan1
          原 LAN1 口  →  lan2
          原 LAN2 口  →  lan3
      显示。

执行：在 nn6000-v1 的 DTS（设备树）文件中用 sed 改 label：
  * 顺序要"倒着改"，先改最后一个不会被后面覆盖：
      LAN2 label  →  lan3
      LAN1 label  →  lan2
      WAN  label  →  lan1
  * 每个 sed 前面先 find + 非空判断，避免 DTS 文件名 / 路径和我们预期不一致时出错。

DTS patch 完成后，配合 2.6.3 board.d 的 LAN 组 "lan1 lan2 lan3"，
开机 LuCI 显示就是 lan1 / lan2 / lan3 三个口，全都在 br-lan 里，不分 WAN。

  2.6.5.2 自定义 MAC 地址（方案 A，DTS + uci-defaults 双保险）
                     ★ 核心目的：解决 LuCI「网络-接口-设备」页每个物理口显示两次
    用户指定：
      lan1 = f8:5e:3c:4c:50:7a
      lan2 = f8:5e:3c:4c:50:7b
      lan3 = f8:5e:3c:4c:50:7c
      br-lan = 跟随 lan1 = f8:5e:3c:4c:50:7a

    为什么用方案 A？
      早期版本（backup-v3 及以前）的做法是：在 uci-defaults 里分别为 lan1/lan2/lan3
      各自 `uci add network device` 一个匿名 section 并写 macaddr。但 LuCI 设备页
      会同时枚举两类数据源：
        ① ubus call network.device status 返回的内核裸接口（必然有 lan1/lan2/lan3）
        ② /etc/config/network 里的所有 config device section（若为每个物理口
          建了 3 个匿名 section，就又多出 3 条 lan1/lan2/lan3）
      两者不去重，导致设备页看到 2*3 + 1(br-lan) = 7 条，重复的 3 条链路速度
      显示为 "-"，看着乱。

    方案 A 分两处写入（MAC 同时进 DTS 和 uci-defaults 兜底，双保险）：
    ┌─────────────────────────────────────────────────────────────────┐
    │ ① DTS patch（Settings.sh 第 2.6.4 节末尾，label rename 之后）  │
    │   对每个 dp 节点（label=lan1/lan2/lan3），在节点末尾的 }; 之前  │
    │   追加两行 DTS 属性：                                           │
    │       mac-address       = [f8 5e 3c 4c 50 XX];                  │
    │       local-mac-address = [f8 5e 3c 4c 50 XX];                  │
    │   lan1 XX=7a, lan2 XX=7b, lan3 XX=7c                            │
    │   NSS-DP 驱动 probe 时会优先读取这两个属性，驱动初始化出来的     │
    │   裸口 MAC 直接就是用户指定值，不需要 UCI 再干预。              │
    │   写入时额外做 3 个保护：                                       │
    │     - awk 取 label 行号、再找到下一个 }; 行号做范围插入，不     │
    │       误插到兄弟节点里                                          │
    │     - 取原闭合行的缩进做新行缩进，对齐 DTS 风格                 │
    │     - sed grep 判重：已有 mac-address 属性的节点跳过，          │
    │       防止重复注入（编译环境多次 reconfigure）                │
    ├─────────────────────────────────────────────────────────────────┤
    │ ② uci-defaults 99-nn6000v1nowifi 里的清理 + 网桥 MAC + 兜底     │
    │   (a) 彻底删除所有遗留的                                        │
    │       · 命名 section：network.lan1 / lan2 / lan3 / br_lan       │
    │       · 匿名 section：name=lan1 / lan2 / lan3 一律删掉（不     │
    │         保留任何物理口 UCI device 绑定！）                      │
    │       · name=br-lan 的匿名 section 只留第一个 board.d 生成     │
    │         的，从第二个起全部删掉（避免 LuCI 两个 br-lan）        │
    │   (b) 只对 br-lan 这个 section 写 UCI：set macaddr（网桥驱动   │
    │       不会从 DTS 读 MAC，必须 UCI 显式指定）+ 若缺 ports 则    │
    │       add_list 补全 lan1/lan2/lan3                              │
    │   (c) uci set network.lan.device='br-lan'（逻辑绑定保险）       │
    │   (d) 最后 4 个 if 块做「首次启动立即生效」兜底：              │
    │       ip link set lan1/lan2/lan3/br-lan address … —— 即便      │
    │       某一版 NSS-DP 驱动暂时忽略了 DTS mac-address，这里也能    │
    │       手动刷对 MAC，重启（uci commit 之后）又由 DTS 再次保证    │
    └─────────────────────────────────────────────────────────────────┘

    方案 A 结果：
      物理口 MAC = DTS 属性（驱动读取）+ 兜底 ip link set（首次启动）；
      UCI network.device section 只剩 1 个：br-lan 网桥（含 ports 3 个 + macaddr）
      LuCI 设备页展示：uBus 裸口（lan1/lan2/lan3）+ 唯一的 br-lan UCI 设备
                       = 共 4 条（3+1），不再重复。

    合法性（不变）：
      * 第 1 字节 0xf8 = 1111_1000，最低位 =0，合法单播
      * 前 5 字节 f8:5e:3c:4c:50 与原厂 OUI 对齐
      * 三个口最后 1 字节 7a/7b/7c，与原厂 79/7a/7b 错开不冲突

  2.6.5.8 清理虚拟模板接口（三层清理兜底，彻底清掉 ip6gre0/ip6tnl0/sit0）★ 新增
    为什么升级成三层？
      第一轮（backup-v3）只做了 1 次 for 循环 + rmmod，但实测刷完机
      `/sys/class/net` 里仍会出现 ip6gre0 / ip6tnl0 / sit0 这三个隧道
      模板口——原因有两种：
        (1) 某模块是 kernel built-in（不是 package ko），GENERAL.txt =n
            根本拦不住，开机就自动注册模板接口；
        (2) 第一轮 rmmod 后，sysfs/kobject 触发一次"模块卸载事件 +
            重新注册"，模板口又被系统建出来了（最典型就是这三个）。
    所以本轮 backup-v4 升级为"三层清理 + 二次 pass + sleep 1 + 末尾收尾"：
      Pass 1: for 清 7 个模板口 → rmmod 9 个模块 → sleep 1 等 sysfs 事件
      Pass 2: 再 for 清一遍 → 再 rmmod 一遍（若 ko 是 built-in，rmmod
              直接 return 1 但被 || true 吞掉，不报错）
      收尾:   最后再 for 一遍，每个模板口额外尝试 ip link delete nomaster
              + delete，保证就算 Pass 2 之后还有残留也被清掉。
    清理的目标接口列表：
      dummy0  erspan0  gre0  gretap0  ip6gre0  ip6tnl0  sit0
    卸载的模块列表：
      dummy  gre  ip_gre  gretap  ip6_gre  ip6_tunnel  sit  ipip  erspan
    结果：开机后 /sys/class/net 只会有 lo + lan1/2/3 + br-lan 这 5 个接口。

  * 打印两行 echo 日志，方便 make 阶段观察注入成功没

           不去重，所以若为 3 个物理口各自建 UCI device section 写 macaddr，

    → 修复（backup-v4 方案 A，backup-v4.1 两个子 bug 修正，推荐）：
         ① MAC 地址改从 DTS 注入：在每个 dp 节点（label=lan1/2/3）}; 前
           追加 mac-address / local-mac-address 属性，驱动 probe 直接读
         ② uci-defaults 里把 name=lan1/lan2/lan3 的匿名 / 命名 device
           section **一律删掉**，不保留任何物理口 UCI device 绑定
         ③ 只对 br-lan 写 UCI device section（网桥 MAC 必须 UCI 指定）
         ④ 末尾加 ip link set 4 个 if 块做兜底（MAC 从两条路保证）
        结果：LuCI 设备页共 4 条 = lan1/2/3 + br-lan，不再重复
    → 子坑 9-a（backup-v4.1 初修，仍有漏网；backup-v4.2 终极修，100% 只剩1个）：
           `uci show network | grep -c @device` = 5 个，但 while 循环只扫到 1 个
           （br-lan），剩下 4 个"没有 name 字段的空壳匿名 device section"

        v4.1 原因 & 临时修复（实测仍漏）：
           条件从 `uci get .name` 换成 `uci -q show @device[N]` 后，真实设备
           上稳定 = 5。反推：libuci 在遇到"完全空、连 type 字段都没有"的
           section 时 exit code 不可靠；或者 board.d/02_network/netifd
           自己在首次启动某个时序额外调过 `uci add network device` 却没写
           name/type，留下 4 个裸空壳，任何遍历判断逻辑都可能漏。
        v4.2 终极修复（暴力清空 + 原子重建 = 绝对只有1个）：
           放弃"遍历 + 按内容判断删"这条路线，改为：
           ① 命名 device section（network.lan1/2/3/br_lan）先 4 行 delete 清光
           ② while 存在 @device[0] → 一直删 @device[0]，**根本不判断内容**
              （每次删后面的自动前移，所以删 0 号永远命中最前面那个，
               空壳/畸形/只含 type 没 name 一律扫光，0 漏网）
           ③ `uci add network device` 明确新建 1 个 @device[0]
           ④ 一次性写齐 4 字段：type=bridge / name=br-lan /
              macaddr=$BR_LAN_MAC（纯 MAC，不带额外引号，注意子坑9-b）

           ① uci-defaults 脚本在 preinit 阶段执行（此时 netifd 还没启动），

           ② 然后才进入 rcS 按优先级启动服务：S20 network（= netifd 启动），
              netifd 读 /etc/board.json 初始化网口时，内部多次调用
              `uci add network device` 却不写 name/type，在 99- 清理完成
              之后又新生成 4 个裸空壳。

           在 base-files/files 下新增 init 脚本
              `/etc/init.d/nn6000-cleanup`，START=21
              （正好在 S20 network 之后，S40 firewall 之前）
           并在 rc.d 建软链 `S21nn6000-cleanup -> ../init.d/nn6000-cleanup`
           start() 函数执行的内容与 99- 的原子重建完全一致：
              删命名 device → while 删 @device[0] 到没有 →
              uci add 1 个 → type/name/macaddr/ports 写齐 →
              uci commit network → ubus call network reload
           预期：START=21 晚于 S20 netifd 启动，这一次重建后不会再有任何
           系统组件再往 UCI 里 `add network device`，所以最终匿名 device
           计数必然 = 1（LuCI 设备页也不再有多的条目）。

           刷完 v5 固件后检查发现 `uci show network | grep -c @device` 仍
           然是 5，且同时还冒出 ip6tnl0 / sit0 两个 IPv6 隧道模板口。
           用户在确认这 3 个问题（device 空壳残留 / resolv.conf 被
           dnsmasq 覆盖成 127.0.0.1 / 虚拟口重启后残留）都不影响系统
           稳定和有线网络功能后，明确决定「放着不动，不折腾」。
           → 故此移除 backup-v4.3 新增的 init.d/nn6000-cleanup +
              S21 软链，恢复成原作者仓库的「没有额外 init 脚本」状态。
           三个观感问题留档在此，后续若有需要再针对性修复。
    → 子坑 9-b（backup-v4.1 修复）：br-lan 配置页 MAC 地址填的是
           `'f8:5e:3c:4c:50:7a'`（外面多一对单引号），实际生效的 MAC 没变
        原因：写了 `uci set "...macaddr='$BR_LAN_MAC'"` — 外层双引号已经
           让 shell 解析变量，内层多写的一对单引号被 shell 当普通字符

v5.1 变更记录（2026-08-03）
================================================================================
变更文件：Scripts/Settings.sh
变更位置：uci-defaults 防火墙清理段（约 L397-L400）

变更内容：
  在防火墙清理逻辑中新增一行清理 rule 的循环：
    while uci -q delete firewall.@rule[0]; do :; done 2>/dev/null

变更原因：
  v5.0 的 uci-defaults 只清理了 firewall.@zone 和 firewall.@forwarding，
  遗漏了 firewall.@rule。原作者 OpenWRT-CI 的防火墙默认配置中有 8 条
  src='wan' 的规则（Allow-DHCP-Renew / Allow-Ping / Allow-IGMP /
  Allow-DHCPv6 / Allow-MLD / Allow-ICMPv6-Input / Allow-ICMPv6-Forward /
  Allow-IPSec-ESP / Allow-ISAKMP），旁路由没有 wan 接口，这些规则
  不会匹配任何流量但属于冗余残留。

  实测发现：SSH 登录设备执行 uci show firewall 可见 8 条 src='wan' 规则
  仍然存在，nft ruleset 中也有对应的空规则链。虽然不影响系统稳定性和
  网络功能，但不够干净。

影响范围：
  仅影响首次启动时的 uci-defaults 脚本执行，对已运行的设备无影响
  （需要重新刷固件才能生效；或手动执行 uci delete firewall.@rule[0] 清理）。
